# AI Usage and Engineering Decision Record

## 1. Purpose

This document describes how artificial intelligence tools were used
during the development of the Empório AI Agent technical challenge
prototype.

The goal is to provide transparency about AI assistance while
distinguishing that assistance from the project author's technical
judgment, implementation review, validation, and final responsibility.

AI was used as an engineering support tool. It was not treated as an
unquestionable authority, an autonomous project owner, or a substitute
for understanding the delivered system.

## 3. AI-assisted technical discussions and decisions

AI was used to explore and discuss technical alternatives. The final
choices remained subject to the project author's review.

### 3.1 Hybrid architecture

**Topic discussed:** How to combine a conversational language model with
deterministic application logic.

**Engineering direction adopted:** The prototype separates explicit
intent routing and deterministic business-data tools from optional
LLM-assisted response rewriting.

**Rationale:** Prices, stock quantities, promotions, order details, and
policy content should be grounded in application data rather than
invented by a language model. Keeping business operations deterministic
also makes important behavior easier to test without an API call.

**Human ownership:** The project author reviewed the architectural
approach and accepted the separation between business-data retrieval and
optional language generation.

### 3.2 Explicit intent routing

**Topic discussed:** How to distinguish customer intents, product names,
commands, and conversational follow-ups.

**Engineering direction adopted:** The agent uses explicit routing rules
and session-level context rather than delegating every decision to the
LLM.

**Rationale:** Explicit rules make core behavior inspectable and
reproducible. They also allow regression tests to target known
ambiguities. The trade-off is that new or unexpected phrasings may
require additional rules and tests.

**Human ownership:** The project author reviewed routing behavior and
the regression cases added during iterative development.

### 3.3 Text normalization

**Topic discussed:** How to improve matching consistency when Portuguese
messages contain accented and unaccented forms.

**Engineering direction adopted:** Text normalization is applied to
message and policy-query processing to reduce differences caused by
diacritics.

**Rationale:** Equivalent expressions such as accented and unaccented
words should be handled more consistently by lexical matching and
routing logic.

**Human ownership:** The project author reviewed the normalization
changes and validated the resulting behavior through the automated test
suite.

### 3.4 Lexical policy retrieval

**Topic discussed:** Whether the prototype required embeddings or a
vector database for retrieving policy information.

**Engineering direction adopted:** The project uses lightweight lexical
retrieval over sections of the supplied policy manual.

**Rationale:** A lexical approach is simpler to run locally, inspect,
and test within the scope of the technical challenge. It avoids
introducing additional infrastructure before demonstrating a need for
it.

**Trade-off:** Token-overlap retrieval may return adjacent or partially
relevant sections. It does not provide semantic retrieval guarantees and
should be evaluated before use with a larger policy corpus.

**Human ownership:** The project author retained responsibility for the
retrieval approach and its documented limitations.

### 3.5 Deterministic data access

**Topic discussed:** How the agent should retrieve catalog, stock,
promotion, and order information.

**Engineering direction adopted:** Business data is accessed through
application functions and parameterized SQLite queries, with CSV files
used as the demonstration data source.

**Rationale:** The LLM should not invent commercial facts or generate
arbitrary SQL. Deterministic tools provide a more controlled and
testable path to business information.

**Human ownership:** The project author reviewed the data-access design
and the boundaries between the agent and the local data layer.

### 3.6 Regression testing

**Topic discussed:** How to reduce regressions as intent routing and
conversation handling evolve.

**Engineering direction adopted:** Automated tests cover representative
behavior, including product discovery, categories, generic inquiries,
policy follow-ups, contextual interactions, and out-of-scope requests.

**Validation record:** The V3.3.0 development environment used Python
3.12 on Windows, where the project test command completed with **41
passing tests**.

**Human ownership:** The project author executed the test suite,
reviewed the results, and remained responsible for deciding whether the
observed behavior was acceptable.

### 3.7 Contextual recommendation refinement (V3.3.3)

**Topic discussed:** How to preserve conversational context when customers answer a recommendation question with short preferences and then request another option.

**Engineering direction adopted:** The agent maintains session-scoped preference fields, the active category and budget, the currently recommended product, and the identifiers of products already recommended. Explicit replies such as string type, supported brand, or maximum price are parsed by deterministic rules. The next recommendation reuses the category, refreshes the catalog query, applies the active filters to catalog data, and excludes previously recommended products.

**Rationale:** This approach makes follow-up behavior inspectable and testable without treating the LLM as the source of product facts. It also makes the no-match condition explicit instead of silently relaxing customer preferences.

**Human ownership:** The project author remains responsible for reviewing the state transitions, catalog filters, test results, and limitations of this rule-based preference parser.

**Validation record:** The V3.3.3 validation run completed with 68 passing automated tests: the 54 V3.3.2 regression tests plus 14 new contextual recommendation tests. The recorded execution environment is not a production deployment or a live-inventory integration.

### 3.8 New catalog search precedence (V3.3.4)

**Topic discussed:** A customer could start a new product search while the agent was waiting for a short recommendation preference. The pending-state handler could interpret the new search's price limit as a preference update, leaving the previous catalog context active.

**Engineering direction adopted:** An explicit catalog-search phrase is now recognized before recommendation and policy follow-up handlers. The active product-search context is reset, and the new message is routed through the regular product-search path. The reset is scoped: customer identity and conversation history remain available, while prior catalog rows, category, budget, preference filters, recommended product, recommendation identifiers, and the pending action are cleared.

**Preserved behavior:** Short replies such as "Nylon" and attribute refinements such as "Yamaha até R$ 1.500" remain contextual when the customer is continuing an existing recommendation flow rather than explicitly starting a new search.

**Rationale:** This prevents stale search results and pending conversational state from overriding a clear customer instruction. The implementation remains deterministic and inspectable; the phrase detector is intentionally bounded and requires regression tests when new phrasings are introduced.

**Human ownership:** The project author remains responsible for reviewing the routing precedence, state reset boundaries, catalog query results, and test evidence.

**Validation record:** The V3.3.4 validation run completed with 73 passing automated tests: 68 retained V3.3.3 tests and 5 new regression tests. The manual conversation was exercised in the validation environment. Windows/Python 3.12 validation remains pending before release publication.

## 4. Human review and decision ownership

AI-generated output was treated as material for consideration and
review.

The project author remained responsible for:

1.  Understanding the challenge requirements and project constraints.
2.  Evaluating technical suggestions rather than accepting them
    automatically.
3.  Selecting the final architecture and implementation approach.
4.  Reviewing code changes and their impact on existing behavior.
5.  Running automated tests and manually exercising the application.
6.  Identifying limitations, trade-offs, and areas requiring further
    validation.
7.  Ensuring that project documentation reflects the delivered
    implementation.
8.  Explaining the system and its technical decisions.

The use of AI does not transfer responsibility for the final
implementation, its correctness, or its limitations.

## 5. Validation practices

The following practices were used to support review of AI-assisted work:

-   **Automated tests:** run the project test suite after relevant
    changes.
-   **Regression-oriented test cases:** add tests for observed routing
    and conversation issues.
-   **Deterministic execution:** retain a mode that can run without an
    LLM, supporting repeatable local evaluation.
-   **Data grounding:** retrieve commercial facts through application
    functions and local structured data.
-   **Documentation review:** describe actual capabilities and known
    limitations rather than claiming unimplemented functionality.
-   **Manual execution:** exercise representative customer conversations
    in the local CLI.

The V3.3.4 validation run recorded 73 passing tests in the project
validation environment. Earlier release-specific results are retained in
the changelog. These results are not a claim of complete test coverage,
production readiness, or a measured model-accuracy score.

## 6. Limitations of AI assistance

AI-generated suggestions can be incomplete, incorrect, or unsuitable for
a particular codebase. They may overlook edge cases, introduce
regressions, or recommend unnecessary complexity.

For that reason:

-   Suggestions require technical review.
-   Generated code requires integration review and testing.
-   Architectural proposals require trade-off analysis.
-   Test suggestions do not replace independent validation.
-   Documentation claims must be checked against the actual
    implementation.

The project does not claim that AI assistance guarantees correctness or
security.

## 7. Transparency statement

AI tools, including ChatGPT, supported parts of the requirements
analysis, architecture discussions, implementation, debugging, test
design, and documentation process.

The project author retained technical ownership of the final decisions
and delivered work. The purpose of using AI was to improve development
efficiency, explore alternatives, support critical analysis, and assist
learning---not to conceal authorship or replace engineering judgment.
